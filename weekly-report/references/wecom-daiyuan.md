# 企业微信 · 大圆（已总结源，实验）

> 企业微信 IM **拿不到原始聊天**（需企业「会话内容存档」，个人办不了，见 `references/wecom.md`）。折中方案：让企微原生 AI **「大圆」**在企微内**先按本 Skill 的规则总结**，你把这份**已过滤的总结**当作**一份原材料**带进来。

## 为什么必须“前置过滤”
大圆默认是“总结群里发生了什么”——接触的全算（别人 @ 你的、群里别人聊的、抄送给你的都会写进去），这和本 Skill「接触 ≠ 参与」相反。**所以必须把过滤规则塞进大圆的 prompt**，让它吐出来就是过滤过的，否则等于把你剔掉的噪音又塞回来。

## 给大圆的 prompt 模板（内嵌 attribution-rules）
在企业微信里唤起大圆，粘贴以下内容（把 `<时间窗>` 换成本周区间，如“本周一到现在”）：
```
帮我总结 <时间窗> 里，【我本人】在工作上真正做的事，用于写周报。严格按下面的规则筛，只留我主动产出的：
- 只提我本人主动发起、推进、决策、承诺或交付的事项。
- 别人 @ 我但我没处理的、群里别人在聊的、只是抄送/知会我的、我只是被邀请/被分配但没动的，一律不要。
- 每条写：事项 - 我做了什么 - 结果/当前状态 - 涉及哪个项目。
- 拿不准是不是我做的，就标「待确认」，不要替我算成已完成。
用 Markdown 无序列表输出。
```
（这段与 `references/attribution-rules.md` 一致，改规则以那份为准。）

## 带进周报时的处理（二手源规矩）
- 大圆的输出是**二手、已总结**，原始信号已丢 → 统一标 **`platform=wecom`、`source_type=summary`、`evidence_level=medium`**。
- **不要再对它做细粒度归因**（没有原始 who/what 可判）；先作为**单列待确认的总结证据**展示，并直接显示其原 `evidence_id`，提示“来自企微大圆总结，请你确认哪些真是你做的”。它此时不是已批准候选；用户对普通候选回复“确认”也不批准这一区。
- 只有用户对具体总结事项**显式确认**后，才能转为候选：若只是补强已有事项，合并来源、保留原 `candidate_id` 并将原 `evidence_id` 追加到 `source_evidence_ids`；若是新事项，生成新 `candidate_id` 并写入该 `evidence_id`。对应 ID 还必须进入 `approved_candidate_ids`；任何无法从 `source_evidence_ids` 追溯到原证据的候选均不得进入白名单。
- 未显式确认的事项，不得进入终稿的**本周进展 / 风险 / 待解决 / 下周计划**；只能保留在数据说明 / 待确认提示中。门禁必须发生在成稿前，不采用事后清理模式。
- 用户把总结贴进来的文本，按敏感原文处理：只放本机临时目录、不外传。
